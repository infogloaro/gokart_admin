GoKart Admin: from Figma prototype to a working product

What has to be built behind the new Super Admin and Admin design, how it fits the company stack, and how three developers can split the work without stepping on each other.

Where things stand

The Figma Make file is a complete, clickable front-end prototype: about 9,300 lines of React across four large files (SuperAdmin.tsx, AdminApp.tsx, FinancePayouts.tsx, financeEngine.ts). Every number, row and status on screen is hard-coded or generated in the browser. Nothing is saved to a server.

  • Super Admin portal, 16 screens: Command Center, Business overview, Food revenue, Mart revenue, Vendors, Delivery partners, Orders, Products & inventory, Complaints & exceptions, Live tracking, Transaction ledger, Finance & payouts (8 tabs), Reports, Admin & permissions, Areas & fees, Audit logs.
  • Admin portal, 12 screens scoped to one business: Dashboard, Overview, Orders, Tracking, Partners, Vendors, Inventory, Complaints, Finance, Reports, Notifications, Profile.
  • Sign-in: email + password, then a 6-digit code, then a workspace picker (ZOAURO FOOD or GLOARO MART). The code is always 123456 and the role is kept in browser session storage.

Your stack document lists PostgreSQL, Redis, Socket.IO and the /api/v1/intake/* endpoints as in use and built. Order status flow, taken from the prototype's labels

Placed → Accepted → Preparing → Ready for pickup (food) / Ready to dispatch (mart) → Assigned → Picked up → Out for delivery → Delivered Any step before Picked up → Cancelled Delivered → Refunded (through a complaint)

Confirm this with operations before Dev 2 builds the state machine; the prototype only shows labels, not the rules.

Splitting the work between three developers

Split by business area, not by front end vs back end. Each developer owns their modules all the way through: Zod schema, Prisma model, API, generated client and the screens. That keeps each person mostly in their own files, and each feature is finished by one person instead of waiting on a hand-off.

Dev 1 · Platform & access

Front-loaded: the others build on the app shell and sign-in, so this person starts first.

  • Design tokens and the shared shadcn component set
  • App shell for both portals: sidebar, top bar, business switcher, routing
  • Sign-in, verification code, TOTP, sessions
  • Members, roles, permissions, zone scoping
  • Areas & fees, Audit logs, Notifications
  • Socket.IO and export-job plumbing used by the others

Dev 2 · Operations

The busiest screens day to day, and the source of the data the money side depends on.

  • Vendors and the vendor onboarding wizard
  • Delivery partners, partner wizard, approval drawer, KYC documents
  • Orders and the order state machine
  • Products & inventory
  • Complaints & exceptions
  • Live tracking; wiring intake events and the simulators

Dev 3 · Money & insight

The most rule-heavy area; financeEngine.ts is already a working spec to port.

  • Transaction ledger
  • Finance & payouts: port the engine to the server in paise
  • Pay-plan change requests and approvals
  • Command Center, Business overview, revenue pages, Admin dashboard
  • Reports and exports
  • Nightly accrual and rollup jobs

Rules that keep three people from colliding

  • One Prisma file per module. Use Prisma's multi-file schema (prisma/schema/orders.prisma, finance.prisma, …). Each developer edits only their own files. Migrations stay additive; rebase on main before generating one.
  • One folder per module in packages/shared, e.g. shared/src/orders/. Cross-module enums (businesses, roles, order status) live in shared/src/common/ and need a review from all three.
  • Never hand-edit packages/api-client. Regenerate it from OpenAPI; if two PRs conflict there, regenerate after merging.
  • Shared UI belongs to Dev 1. Others open a small PR against it rather than copying a component.
  • Agree the cross-module contracts in Week 1: the Order, Partner and Vendor shapes Dev 3 reads, and the ledger events Dev 2 emits. Dev 3 builds against seed data and the simulators until real orders flow.
  • Add a CODEOWNERS file matching the split, branch as feat/<module>-<change>, and require one review from another developer on every PR.

Definition of done for every module

  • Zod schemas in packages/shared, used by both the form and the API
  • Prisma model and an additive migration, plus seed data
  • Route → controller → service → repository, with permission and zone checks on the server
  • Every write audited; money in paise; order changes through the state machine
  • OpenAPI updated and api-client regenerated
  • Screen wired with TanStack Query, with loading, empty and error states
  • Vitest + Supertest for the API, one Playwright happy path for the screen

Decisions needed from the owner

  • Pay rules. The prototype's partner pay (salary, fixed amount, per-delivery rate, % of delivery fees) and admin pay (salary, % commission, on-time target and incentive) are assumptions. Confirm them before Dev 3 builds payouts.
  • Order states. Confirm the flow above, including who may cancel at each step.
  • Paying out. Until Razorpay payouts are live, "Mark as paid" records a bank reference (UTR) by hand. Confirm that is acceptable.
  • Sign-in codes. Email now, SMS after DLT registration, as planned.
  • Map provider. Live tracking stays on OpenStreetMap until the Phase 2 choice.
